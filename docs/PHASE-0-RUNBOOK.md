# Фаза 0 — аварийный runbook

> **Выполнено 2–3 августа 2026.** Документ оставлен как запись того, что и в каком порядке делалось: если однажды снова утечёт ключ или понадобится закрыть прод, порядок шагов здесь верный. Повседневные команды — в [шпаргалке](CHEATSHEET.md).
>
> Единственный незакрытый пункт — проверить, что старый ключ не остался в метаданных виртуальной машины в Yandex Cloud (шаг 7).

Пошаговая инструкция. Рассчитана на 1-1.5 часа. Команды для macOS.

**Общее правило на всю фазу:** не закрывайте текущую SSH-сессию к серверу, пока не убедились, что новый способ входа работает. Всё, что может запереть вас снаружи, проверяется из **второго окна терминала** при живом первом.

Порядок шагов не случаен. Сначала бэкап (страховка), потом ротация ключа (закрывает доступ), потом чистка истории (косметика после того, как ключ уже мёртв), потом Basic Auth.

## Шаг 1. Бэкап базы — до всего остального

Если что-то пойдёт не так на любом следующем шаге, у вас будет год статистики на своей машине.

```bash
mkdir -p ~/dog-walks-backups
scp ubuntu@103.76.53.197:/opt/dog-walks-app/backend/database/walks.db \
    ~/dog-walks-backups/walks-$(date +%Y%m%d).db
```

`scp` — это копирование файлов поверх SSH. Синтаксис `откуда куда`, где удалённый путь пишется как `пользователь@адрес:/путь/к/файлу`.

Проверьте, что файл приехал целым:

```bash
ls -lh ~/dog-walks-backups/
sqlite3 ~/dog-walks-backups/walks-$(date +%Y%m%d).db "SELECT COUNT(*) FROM walks;"
```

`sqlite3` есть в macOS из коробки. Ожидаемый результат — число около 260. Если команда ругается «file is not a database», значит скопировалось не то, разбираемся до перехода дальше.

> Если путь `/opt/dog-walks-app/...` не существует — зайдите на сервер (`ssh ubuntu@103.76.53.197`) и найдите базу: `sudo find / -name "walks.db" 2>/dev/null`

## Шаг 2. Сгенерировать новый ключ

```bash
ssh-keygen -t ed25519 -C "andrey.pit@gmail.com" -f ~/.ssh/id_ed25519_dogwalks
```

Вот здесь и кроется исходная ошибка. Флаг `-f` явно задаёт, **куда** сохранить ключ. В прошлый раз его не было, `ssh-keygen` спросил путь интерактивно, а в ответ ему прилетела вся строка команды целиком — так и появился файл с именем `ssh-keygen -t ed25519 -C "andrey.pit@gmail.com"` в папке проекта, вместо `~/.ssh/id_ed25519`.

Программа спросит passphrase. **Задайте его.** Это пароль на сам файл ключа: если ключ утечёт снова, без passphrase им не воспользуются. macOS запомнит его в Keychain, вводить каждый раз не придётся.

Создались два файла:

| Файл | Что это | Куда можно |
|---|---|---|
| `~/.ssh/id_ed25519_dogwalks` | **приватный** ключ | никуда. Только на вашей машине |
| `~/.ssh/id_ed25519_dogwalks.pub` | **публичный** ключ | куда угодно: на сервер, в GitHub, в чат |

Именно первый лежал в публичном репозитории. Разница на глаз: приватный начинается с `-----BEGIN OPENSSH PRIVATE KEY-----` и занимает несколько строк, публичный — одна строка вида `ssh-ed25519 AAAAC3... andrey.pit@gmail.com`.

Проверьте права (SSH откажется работать с ключом, доступным другим пользователям):

```bash
chmod 600 ~/.ssh/id_ed25519_dogwalks
chmod 644 ~/.ssh/id_ed25519_dogwalks.pub
```

## Шаг 3. Настроить алиас, чтобы не печатать IP

Откройте (или создайте) `~/.ssh/config`:

```bash
nano ~/.ssh/config
```

Добавьте:

```
Host dogwalks
    HostName 103.76.53.197
    User ubuntu
    IdentityFile ~/.ssh/id_ed25519_dogwalks
    IdentitiesOnly yes
```

Сохранить в nano: `Ctrl+O`, `Enter`, затем `Ctrl+X`.

`IdentitiesOnly yes` заставляет SSH использовать именно этот ключ и не перебирать все остальные. Без него при большом количестве ключей сервер может отклонить соединение, исчерпав лимит попыток.

Теперь вместо длинной команды достаточно `ssh dogwalks`. Но проверять это будем на шаге 5, не сейчас.

## Шаг 4. Положить новый публичный ключ на сервер

```bash
cat ~/.ssh/id_ed25519_dogwalks.pub | ssh ubuntu@103.76.53.197 "cat >> ~/.ssh/authorized_keys"
```

Читаем публичный ключ и дописываем его в конец файла `~/.ssh/authorized_keys` на сервере. Этот файл — просто список публичных ключей, которым разрешён вход. `>>` означает «дописать в конец», а не «перезаписать»: одна лишняя `>` здесь стёрла бы все существующие ключи и заперла вас снаружи.

Эта команда выполнится по старому ключу — он ещё работает, это нормально.

## Шаг 5. Проверить новый ключ, не закрывая старую сессию

**Не пропускайте этот шаг.** Дальше мы удалим старый ключ, и если новый не работает, попасть на сервер будет нечем.

В первом окне терминала откройте живую сессию и оставьте её:

```bash
ssh ubuntu@103.76.53.197
```

Во **втором** окне (`Cmd+T` — новая вкладка):

```bash
ssh dogwalks
```

Должен пустить, спросив passphrase от ключа. Если пустил — идём дальше. Если нет, диагностика:

```bash
ssh -v dogwalks
```

Флаг `-v` показывает, какие ключи SSH пробует и что отвечает сервер. Ищите строки `Offering public key` и `Authentications that can continue`.

## Шаг 6. Удалить старый ключ с сервера

В сессии на сервере:

```bash
cp ~/.ssh/authorized_keys ~/.ssh/authorized_keys.backup
cat -n ~/.ssh/authorized_keys
```

`cat -n` покажет файл с номерами строк. Каждая строка — один ключ. Нужно понять, какая из них старая, скомпрометированная.

Сравните с содержимым утёкшего публичного ключа. На своей машине, в папке проекта:

```bash
cat 'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com".pub'
```

Кавычки обязательны — в имени файла есть пробелы и кавычки.

Найдите в `authorized_keys` строку с тем же самым набором символов после `ssh-ed25519 ` и удалите **её**, а не новую. Новый ключ — тот, что вы добавили последним, он в самом низу файла.

```bash
nano ~/.ssh/authorized_keys
```

Удалить строку в nano целиком: поставить курсор на неё и нажать `Ctrl+K`. Сохранить: `Ctrl+O`, `Enter`, `Ctrl+X`.

Теперь **из третьего окна** проверьте, что вход новым ключом всё ещё работает:

```bash
ssh dogwalks
```

Если да — старую сессию можно закрывать. Если нет — вы всё ещё внутри по первой сессии, восстановите файл: `cp ~/.ssh/authorized_keys.backup ~/.ssh/authorized_keys` и разбирайтесь.

## Шаг 7. Метаданные VM в Yandex Cloud — про это обычно забывают

Yandex Cloud раздаёт SSH-ключи на виртуалку через **метаданные VM**: при создании машины вы вставили публичный ключ в поле «SSH-ключ», и `cloud-init` прописал его в `authorized_keys` при первой загрузке.

Проблема: если старый ключ остался в метаданных, он может вернуться в `authorized_keys` при пересоздании машины или переустановке cloud-init. Шаг 6 без шага 7 — половина работы.

1. Консоль Yandex Cloud → **Compute Cloud** → Виртуальные машины → `dog-walks-server`
2. Кнопка **Изменить** (или ⋮ → Редактировать)
3. Блок **Доступ** → поле **SSH-ключ**
4. Удалите старый публичный ключ, вставьте новый — содержимое `~/.ssh/id_ed25519_dogwalks.pub`
5. Сохранить

Скопировать новый публичный ключ в буфер обмена:

```bash
pbcopy < ~/.ssh/id_ed25519_dogwalks.pub
```

Пока вы в консоли облака, загляните в **Группы безопасности** (Virtual Private Cloud → Группы безопасности). Проверьте правила для входящего трафика: порт 22 в идеале должен быть открыт не для `0.0.0.0/0`, а для вашего домашнего IP. Но это опционально и рискованно при динамическом IP от провайдера — если не уверены, оставьте как есть, вернёмся в Фазе 3.

## Шаг 8. Проверить GitHub

Ваш remote настроен по HTTPS (`https://github.com/an-pit/dog-walks.git`), значит для пушей используется токен, а не SSH-ключ. Скорее всего, утёкший ключ в GitHub не добавлялся. Но проверить стоит.

1. github.com → аватар → **Settings** → **SSH and GPG keys**
2. Если там есть ключ с отпечатком старого — удалите

Отпечаток старого ключа можно посчитать локально:

```bash
ssh-keygen -lf 'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com".pub'
```

Выведет строку вида `256 SHA256:xxxxx... andrey.pit@gmail.com (ED25519)`. GitHub показывает отпечатки в том же формате — сравнивайте по части после `SHA256:`.

## Шаг 9. Посмотреть, не заходил ли кто чужой

На сервере:

```bash
sudo last -30
sudo grep "Accepted publickey" /var/log/auth.log | tail -50
sudo grep -c "Failed password" /var/log/auth.log
pm2 logs --lines 200 --nostream
```

- `last` — история входов: кто, откуда, когда
- `Accepted publickey` — успешные входы по ключу с указанием IP
- `Failed password` — счётчик неудачных попыток. Большое число (тысячи) — это нормально, интернет постоянно перебирает пароли на любой публичный сервер. Тревожно, только если после этого идёт `Accepted`

Свой домашний IP посмотрите на whatismyip.com и сверьте: всё, что не он и не ваш мобильный интернет, — повод присмотреться.

**Важное ограничение:** `auth.log` ротируется, обычно хранится 4 недели. Ключ лежал в открытом доступе с апреля — почти три месяца, и логи за этот период уже стёрты. Старые архивы можно поискать: `ls /var/log/auth.log*`, файлы `.gz` читаются через `sudo zgrep "Accepted" /var/log/auth.log.*.gz`.

**Про «ключ не был скомпрометирован».** Понимаю логику, но сформулирую точнее: отсутствие следов взлома — это не то же самое, что отсутствие компрометации. Приватный ключ три месяца лежал в публичном репозитории. GitHub непрерывно сканируется ботами, которые ищут именно такие файлы, и в такой формулировке ключ считается скомпрометированным по факту публикации, независимо от того, воспользовался им кто-то или нет. Практический вывод не меняется — вы ключ меняете, — но привычка считать «утёк = скомпрометирован» пригодится дальше, когда появятся токены доступа и пароли к БД.

## Шаг 10. Вычистить ключ из истории git

Ключ уже мёртв, так что это не срочно — но нужно, чтобы репозиторий можно было спокойно показывать.

**Почему обычного удаления файла не хватит.** Git хранит каждую версию каждого файла. Коммит с удалением добавляет новую версию, где файла нет, но старая остаётся в истории и доступна по `git show b0420c0:'ssh-keygen...'`. Чтобы убрать по-настоящему, историю надо переписать.

### 10.1. Резервная копия папки

```bash
cd ~/путь/к/родительской/папке
cp -R dog-walks-app dog-walks-app-backup-$(date +%Y%m%d)
```

### 10.2. Установить git-filter-repo

```bash
brew install git-filter-repo
```

Если нет Homebrew — поставить с brew.sh, либо `pip3 install git-filter-repo`.

### 10.3. Переписать историю на свежем клоне

`git filter-repo` намеренно отказывается работать в папке с незакоммиченными изменениями и остатками старой истории. Правильный путь — свежий клон:

```bash
cd ~
git clone https://github.com/an-pit/dog-walks.git dog-walks-clean
cd dog-walks-clean

git filter-repo \
  --path 'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com"' \
  --path 'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com".pub' \
  --invert-paths
```

`--path` указывает файлы, `--invert-paths` переворачивает смысл: не «оставить только эти», а «выбросить эти». Инструмент пройдёт по всем коммитам и пересоберёт их без указанных файлов.

Убедитесь, что файлов больше нет нигде в истории:

```bash
git log --all --oneline --name-only | grep -c "ssh-keygen"
```

Должно вывести `0`.

### 10.4. Force push

`filter-repo` из соображений безопасности удаляет remote — чтобы вы не запушили переписанную историю случайно. Возвращаем и пушим осознанно:

```bash
git remote add origin https://github.com/an-pit/dog-walks.git
git push origin --force --all
```

`--force` перезаписывает историю на GitHub. Это разрушительная операция, и именно поэтому мы сделали копию в 10.1. Для репозитория, где вы единственный разработчик, она безопасна.

Откройте github.com/an-pit/dog-walks и убедитесь, что файлов в списке нет.

> **Нюанс:** GitHub какое-то время держит старые коммиты доступными по прямой ссылке с хешем, пока не отработает сборка мусора. Полностью выбить их можно только через обращение в GitHub Support. Но раз ключ уже ротирован, это уже не имеет значения — ровно поэтому ротация шла первой, а чистка истории десятой.

### 10.5. Перевести рабочую папку на чистую историю

Ваша локальная папка `dog-walks-app` содержит старую историю и после force push будет расходиться с GitHub. Проще всего перейти на свежий клон.

Сохраните файлы, которых нет в git (`AUDIT-AND-ROADMAP.md`, `PHASE-0-RUNBOOK.md`, `dog-walks-manual.md`), скопируйте их в `dog-walks-clean`, и дальше работайте оттуда. Старую папку не удаляйте ещё пару недель — пусть полежит.

### 10.6. Закрыть дыру на будущее

В `.gitignore` добавьте:

```
# Ключи и секреты
*.pem
*.key
id_rsa*
id_ed25519*
*ssh-keygen*
.env*
!.env.example
```

Заодно уберите `.DS_Store` из отслеживания:

```bash
git rm --cached .DS_Store frontend/.DS_Store
```

И включите защиту на стороне GitHub: репозиторий → **Settings** → **Code security** → **Secret scanning** и **Push protection**. Push protection блокирует пуш, если в нём обнаружен похожий на секрет текст. Для публичных репозиториев это бесплатно и должно было бы поймать ситуацию с ключом ещё в апреле.

Удалите локальные копии старого ключа из папки проекта:

```bash
rm 'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com"' \
   'ssh-keygen -t ed25519 -C "andrey.pit@gmail.com".pub'
```

## Шаг 11. Закрыть API паролем

Временная мера на nginx, пока не готова настоящая авторизация. Займёт 10 минут.

На сервере:

> ⚠️ **Эти команды запускаются строго по одной.** `htpasswd` спрашивает пароль, и если вставить блок целиком, следующая строка будет съедена в качестве ответа на приглашение `New password:`. То же касается `ssh-keygen`, `passwd`, `certbot` и `apt` без `-y`.

```bash
sudo apt update && sudo apt install apache2-utils -y
```

Дождитесь окончания, затем отдельно:

```bash
sudo htpasswd -c /etc/nginx/.htpasswd andrey
```

Появится `New password:` — вводимые символы не отображаются, это нормально. Затем `Re-type new password:`. Ожидаемый ответ: `Adding password for user andrey`.

Только после этого:

```bash
sudo htpasswd /etc/nginx/.htpasswd ira
```

`-c` создаёт файл, поэтому он только в первой команде — во второй его быть не должно, иначе файл перезапишется и первый пользователь пропадёт.

Проверьте результат — должно быть ровно две строки вида `andrey:$apr1$...`:

```bash
sudo cat /etc/nginx/.htpasswd
```

Права на файл:

```bash
sudo chown root:www-data /etc/nginx/.htpasswd
sudo chmod 640 /etc/nginx/.htpasswd
```

Правим конфиг:

```bash
sudo nano /etc/nginx/sites-available/dog-walks
```

Добавьте две строки **на уровень `server`**, сразу после `server_name` — так защита накроет и фронтенд, и `/api` разом:

```nginx
server {
    listen 80;
    server_name 103.76.53.197;

    auth_basic "Dog Walks";
    auth_basic_user_file /etc/nginx/.htpasswd;

    location / {
        ...
    }
}
```

Проверить синтаксис и применить:

```bash
sudo nginx -t
sudo systemctl reload nginx
```

`nginx -t` проверяет конфиг, не применяя его. Всегда запускайте его перед `reload` — иначе опечатка уронит сайт.

Проверка, что сработало:

```bash
curl -I "http://103.76.53.197/api/walks?from=2026-08-01&to=2026-08-02"
```

Ожидаем `HTTP/1.1 401 Unauthorized`. Если по-прежнему `200` — конфиг не тот, посмотрите `ls /etc/nginx/sites-enabled/`.

**Честно про ограничения этой меры.** Basic Auth поверх HTTP передаёт логин и пароль в base64 — это кодирование, а не шифрование, расшифровывается тривиально. От случайного прохожего и от ботов-сканеров защищает, от того, кто слушает трафик в вашей Wi-Fi-сети или у провайдера — нет. Для данных о прогулках с собакой это приемлемый размен на ближайшие недели. Поэтому: **возьмите пароль, который больше нигде не используется.**
