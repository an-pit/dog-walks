Что проверялось: код в репозитории (2 коммита), публичный репозиторий `an-pit/dog-walks`, прод `http://103.76.53.197/`

## Часть 1. Что нашли

### 🔴 Критично — чинить сегодня

**1. Приватный SSH-ключ лежит в публичном репозитории**

Файл `ssh-keygen -t ed25519 -C "andrey.pit@gmail.com"` — это не команда, а результат её выполнения: приватный ключ, содержимое начинается с `-----BEGIN OPENSSH PRIVATE KEY-----`. Рядом лежит `.pub`. Оба закоммичены в `b0420c0` и с апреля доступны любому в интернете.

Похоже, при создании ключа команда была введена так, что имя файла стало самой командой. Классическая ошибка, но последствия реальные: если этот ключ прописан в `authorized_keys` на VM в Yandex Cloud или добавлен в GitHub → Settings → SSH keys, то доступ к серверу и/или к репозиторию открыт всем.

**Важно:** удалить файл новым коммитом недостаточно — ключ останется в истории git и в кэше GitHub. Нужна ротация + переписывание истории. Порядок действий в Фазе 0.

**2. API полностью открыт — нет никакой аутентификации**

Проверено вживую, без каких-либо ключей:

```
GET http://103.76.53.197/api/walks?from=1900-01-01&to=2100-01-01
→ вся база, 250+ записей
```

`PUT /api/walks/:date/:slot` тоже открыт. То есть любой, кто знает IP, может прочитать всю вашу статистику, перезаписать любую запись или обнулить историю за все месяцы. IP-адрес светится в этом документе, в истории браузера, в логах любого сервиса, куда вы заходили с этого сервера.

**3. Прод работает по HTTP без TLS**

Сейчас утечка ограничена самими данными о прогулках. Но как только появится форма логина (Фаза 4), пароли будут ходить открытым текстом. HTTPS обязателен до включения авторизации, не после.

---

### 🟠 Высокий приоритет

**4. Прод рассинхронизирован с репозиторием**

В коде и во фронтенде есть поле `comments` (`DurationModal.jsx`, `server.js`), но прод его не возвращает — в JSON-ответе колонки `comments` просто нет. Значит на сервере либо старый билд, либо не прогнана миграция после добавления поля.

Это не косметика, а симптом главной проблемы процесса: **никто не знает, что именно сейчас крутится в проде.** Ровно это и должен решать нормальный деплой.

**5. Нет ограничения на диапазон дат**

`from=1900-01-01&to=2100-01-01` выгружает всю базу одним запросом. При росте данных это и утечка, и способ положить сервер.

**6. Нет rate limiting**

Ничто не мешает слать тысячи PUT-запросов в секунду. При SQLite это быстро упрётся в блокировки записи.

**7. CORS открыт для всех** (`app.use(cors())` без опций)

Любой сторонний сайт может дёргать ваш API из браузера посетителя. После введения cookie-сессий это станет вектором CSRF.

**8. Нет бэкапов**

В `DEPLOYMENT.md` описан скрипт бэкапа, но непонятно, настроен ли он в cron. Даже если настроен — копии лежат на том же диске той же VM. Диск умрёт или VM удалится — данных нет. Год статистики прогулок восстановить будет неоткуда.

**9. Нет security-заголовков** (`helmet` не подключён), нет ограничения размера тела запроса, поле `comments` не ограничено по длине — можно записать мегабайты текста в одну ячейку.

---

### 🟡 Средний приоритет

**10. Хардкод «Андрей и Ира» на всех уровнях.** Имена зашиты в CHECK-констрейнт БД (`person IN ('andrey','ira','both','none')`), в валидацию API, в константы фронтенда (`PERSONS`). При переходе на регистрацию пользователей всё это переписывается целиком. Это главный архитектурный долг и главная причина, почему Фаза 4 такая большая.

**11. Миграции не версионируются.** Один `migrate.js`, который создаёт таблицу «если её нет». Добавить колонку через него нельзя — что и объясняет пункт 4. Нужны пронумерованные миграции.

**12. Возможный баг с часовым поясом.** `dateUtils.formatDate` использует `toISOString()`, который переводит время в UTC. Для пользователя в UTC+3 поздним вечером дата может «уехать» на предыдущую. Коммит `4e15881` называется «fix timefix» — вероятно, вы это уже ловили, но стоит проверить целенаправленно.

**13. Не проверяется, что `from` <= `to`.**

**14. Нет health-check эндпоинта** — автодеплой не сможет убедиться, что сервис реально поднялся.

**15. Одна ветка `main`, пуш напрямую.** Нет истории изменений по смыслу, нет возможности отката, нет ревью.

**16. Мусор в репозитории:** `.DS_Store`, три пересекающихся файла инструкций (`DEPLOYMENT.md`, `GITHUB_DEPLOYMENT.md`, `GITHUB_INSTRUCTIONS.md`), ключи. Стоит почистить и свести документацию в один README.

**17. Устаревшие зависимости.** Vite 4, Express 4, `better-sqlite3` 9. Обновить и настроить Dependabot.

## Часть 2. План работ

Выбранное направление: полноценная регистрация пользователей, авто-деплой через GitHub Actions, безопасность в первую очередь, тесты API + smoke.

---

### Фаза 0 — Аварийная. Сегодня, ~1-1.5 часа

Делаем до всего остального, потому что пока ключ жив, всё остальное не имеет смысла.

1. **Снять бэкап прод-базы прямо сейчас**, до любых изменений. `scp` файла `walks.db` к себе на машину. Это страховка на весь остаток работ.
2. **Сгенерировать новый SSH-ключ** правильной командой:
   `ssh-keygen -t ed25519 -C "andrey.pit@gmail.com" -f ~/.ssh/id_ed25519_dogwalks`
3. **Добавить новый публичный ключ** на VM (`~/.ssh/authorized_keys`) и проверить, что вход работает **в отдельном терминале, не закрывая текущую сессию** — иначе есть шанс запереть себя снаружи.
4. **Удалить старый публичный ключ** из `authorized_keys` на VM и из GitHub → Settings → SSH and GPG keys.
5. **Вычистить ключ из истории git** — `git filter-repo` или BFG, затем force push. Обычный `git rm` не поможет.
6. **Проверить логи на следы чужих входов:** `sudo last -20`, `sudo grep "Accepted" /var/log/auth.log`, `pm2 logs --lines 200`.
7. **Временно закрыть API** — Basic Auth на уровне nginx, одна пара логин/пароль на двоих. Это заглушка на 2-3 недели, пока не готова настоящая авторизация.

Что прокачивается: как устроены SSH-ключи, чем `authorized_keys` отличается от GitHub keys, почему история git — это навсегда.

---

### Фаза 1 — Процесс разработки. Неделя 1

Сначала строим рельсы, потом едем. Все дальнейшие правки идут уже через новый процесс — это и есть тренировка.

- Локальное окружение, которое поднимается одной командой; `.env` с примером `.env.example` в репозитории
- Ветки: `main` = то, что в проде. Работа в `feature/*`, вливание через Pull Request. Даже в одиночку — PR даёт вам самому посмотреть на диff перед выкаткой
- Branch protection на `main`: запрет прямого пуша, обязательный прохождённый CI
- Vitest + supertest: тесты на все 4 эндпоинта — валидация входных данных, граничные случаи, отказы
- GitHub Actions: на каждый PR прогоняются тесты и линтер
- Отдельная тестовая БД, чтобы тесты не трогали реальные данные
- `CLAUDE.md` в корне с описанием проекта, чтобы контекст не терялся между сессиями
- Чистка репозитория: `.DS_Store`, лишние инструкции, объединение документации

Что прокачивается: ветки и PR, GitHub Actions, что вообще тестировать в API.

### Фаза 2 — Деплой. Недели 1-2

- `ecosystem.config.js` (PM2) переносится в репозиторий — сейчас он существует только на сервере, вне контроля версий
- Пронумерованные миграции; деплой прогоняет их автоматически. Заодно чинится расхождение с `comments`
- Эндпоинт `GET /api/health` — отдаёт статус и версию сборки
- Отдельный **deploy key** для GitHub Actions: свой ключ только для деплоя, положенный в GitHub Secrets. Ваш личный ключ в CI не используется
- Workflow: push в `main` → тесты → сборка фронта → выкатка на VM → миграции → перезапуск PM2 → smoke-тест `/api/health` → при провале автоматический откат
- Автобэкап БД **в Yandex Object Storage**, не на диск той же VM. Ежедневно, хранение 30 дней

Что прокачивается: GitHub Secrets, деплой-ключи, PM2, идея «прод собирается из git, а не правится руками».

### Фаза 6 — Авторизация и мультипользовательность

Самая объёмная часть. Схема БД меняется целиком.

Примерная новая структура:

```
users        (id, email, password_hash, name, role, created_at)
households   (id, name)            — «семья»: вы с Ирой в одной
memberships  (user_id, household_id, role)
dogs         (id, household_id, name)
walks        (id, dog_id, user_id, walk_date, slot, duration, comments, created_at)
```

Работы:

- Хеширование паролей (argon2 или bcrypt), сессии в httpOnly-cookie
- Регистрация, вход, выход, смена пароля
- Изоляция данных: каждый видит только прогулки своего домохозяйства
- Убрать хардкод `andrey`/`ira` из БД, API и фронта
- **Миграция существующих данных**: 260+ записей с `person = 'andrey'/'ira'/'both'` привязать к новым user_id. Записи `both` разворачиваются в две. Планируется отдельно, проверяется на копии базы
- Админка: список пользователей, блокировка, общая статистика

Схему входа обсудим ближе к делу — идея с «название питомца + код» рабочая и снимает вопрос с email и восстановлением пароля.

## Часть 3. Принятые решения

**Домен и HTTPS — отложены.** Служебного публичного домена Yandex Cloud не даёт: Cloud DNS умеет либо внутренние зоны (видны только внутри VPC), либо публичные — но для публичной нужен домен, которым вы уже владеете. Варианты вроде `nip.io` / `sslip.io` формально работают, но их общая квота в Let's Encrypt регулярно исчерпывается (последний раз в феврале 2026), так что автопродление сертификата будет периодически отваливаться — для прода это не годится. Остаётся либо купить домен за ~200-400 ₽/год, либо жить на HTTP.

На ближайшие недели живём на HTTP под Basic Auth. **Ограничение, которое надо держать в голове:** Basic Auth кодирует пароль в base64, а не шифрует. Это защита от ботов-сканеров и случайных прохожих, но не от прослушивания трафика. Как только дойдём до формы логина — домен придётся купить, вариантов не останется.

**SQLite остаётся, и переубеждать не буду.** Для нескольких десятков пользователей его хватает с большим запасом, а сложность Фазы 6 определяется не движком БД, а тем, что имена «andrey/ira» зашиты в схему, в API и во фронт — при Postgres переписывать пришлось бы ровно столько же. Плюс у SQLite есть практическое преимущество прямо сейчас: бэкап — это копирование одного файла.

Две вещи стоит сделать по ходу дела: включить WAL-режим (`PRAGMA journal_mode = WAL`) — он заметно улучшает поведение при одновременных чтении и записи, и помнить, что `better-sqlite3` работает синхронно и блокирует event loop. На ваших объёмах это незаметно, но при тяжёлых запросах отзовётся.

Переезд на Postgres имеет смысл обсуждать, только если приложение реально пойдёт в публичный доступ с сотнями пользователей. Тогда это будет отдельная задача на пару дней, не катастрофа.

**Авторизация — после функциональности.** Приоритет: безопасность инфраструктуры → процесс → доработки → HTTPS → аккаунты.

**Привязка истории прогулок** к аккаунтам решается через настройки аккаунта, схема прорабатывается в Фазе 6.
